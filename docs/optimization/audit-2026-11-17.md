# 최적화 및 정리 점검 — 2026-11-17

## 성능 개선 순서

### 1. 화면별 코드 분리

- 최신 메인 JS: 571,804 bytes, gzip 183,187 bytes. 빌드의 500 kB 청크 경고 대상이다.
- src/main.tsx에서 Gate, Cham, Circle, RPS, Dodge, Community 화면을 정적으로 import한다.
- 우선 게임 플레이/결과 화면과 커뮤니티 화면을 경로별 lazy import로 나누는 것을 권장한다.
- 홈 최고 기록을 읽는 readCham/readRps/readDodge가 게임 화면 모듈에 함께 있어, 읽기 함수를 가벼운 기록 모듈로 먼저 분리해야 효과가 난다.
- 사용자 요청으로 제거한 로딩 스크린을 다시 추가하지 않는다. 진입 직전 필요한 모듈을 미리 받는 방식과 기존 화면 유지 방식으로 검토한다.
- 효과는 분리 후 초기 JS 크기와 첫 진입/재진입 시간을 비교해 판단해야 한다. 현재 실기기 속도 개선을 측정한 것은 아니다.

### 2. 벽 통과!의 프레임 처리 비용

- body.worker.ts는 캔버스를 재사용하지만 마스크 ImageData는 매 결과마다 새로 만든다. 크기가 같으면 픽셀 버퍼를 재사용할 수 있다.
- 매 누끼 프레임에 대해 메인 스레드의 GateCutout이 변환·허리 페이드 합성을 하고, CSS drop-shadow 네 개를 추가한다. 저사양 장치에서는 이 비용을 따로 측정할 필요가 있다.
- GateGamePage는 40ms마다 게임 상태를 setState한다. 카메라의 setBody 갱신과 함께 React 렌더가 발생한다. HUD/규칙 상태와 연속적인 벽 애니메이션을 분리하는 방안을 검토한다.
- 이미 적용된 보호 장치: 추론 프레임 큐 없음, 512px 누끼 출력 제한, 느린 추론에 따른 갱신 간격 조절, 오래된 프레임 제거, Bitmap.close(), 원본 카메라 프레임과 마스크의 시점 일치.
- 1순위는 메모리 할당 재사용이다. 추론 해상도/FPS/신뢰도 임계값 변경은 인식률을 떨어뜨릴 수 있으므로 실카메라 비교 후 결정한다.

### 3. 이미지 크기 조절

- 게임 카드·랜딩용 WebP 7개가 각각 약 593–876 KiB다. 전체 배포 이미지 약 6.55 MiB.
- 현재 prepare-characters.mjs는 무손실 WebP를 만들며 카드용 7개는 원본 해상도를 유지한다. 실제 표시 폭에 맞춘 작은 카드용 변형과 큰 화면용 변형을 나누면 다운로드/디코딩 비용을 줄일 여지가 있다.
- Character는 이미 lazy loading과 async decoding을 사용한다. 모든 이미지를 홈에서 선로딩한다고 판단해서는 안 된다.
- 투명 가장자리와 쏴!의 알파 히트박스를 유지해야 한다. 원본 char 삭제나 일괄 손실 압축은 권장하지 않는다.

### 4. WASM 배포 구성 검토

- prepare-vision.mjs는 일반/SIMD module/no-SIMD 세 런타임을 복사한다. JS까지 약 33.8 MiB.
- 세 worker의 FilesetResolver.forVisionTasks 호출은 useModule=true다. 설치된 SDK는 SIMD 지원 여부와 useModule 값으로 파일 이름을 결정한다.
- 따라서 실제 지원 브라우저에서 선택되는 경로를 확인한 뒤 사용하지 않는 런타임을 배포에서 제외할 여지가 있다. 용량만 보고 런타임을 즉시 지우면 안 된다. 특히 no-SIMD 환경의 파일 선택/지원 여부를 검증해야 한다.
- 다운로드는 필요한 런타임과 모델을 카메라 연결 시 선택해서 수행하므로 전체 dist 크기를 카메라 시작 다운로드 크기로 해석하지 않는다.

### 추가 정리 가능하지만 보존 여부 결정이 필요한 파일

- artifacts/audio-tools 약 83.66 MiB: normalize-bgm.py를 다시 실행할 때 FFmpeg를 별도로 마련할 수 있으면 정리 가능. 현재 BGM 갱신 점검이 필요하므로 그 작업 후 정리가 적절하다.
- 전체 비교 worktree 두 개 약 705.46 MiB: 앞으로 과거 버전 비교가 불필요한 경우 Git worktree 명령으로 제거한다. 탐색기에서 폴더만 삭제하면 Git 등록이 남는다.
- 다수 스크린샷·일회성 add-endless*.mjs/add-seeker.mjs/connect-gate-pose.mjs: 배포 입력은 아니지만 변경 검토 증빙과 이력이다. 최종 캡처/측정 원시 JSON/DB 적용 증빙을 남기고 이전 중간본부터 선별한다.
- dist/test-results: 재생성 가능하지만 현재 미리보기 서버나 테스트가 사용 중인지 확인한다. 루트 node_modules를 지우는 것은 일상 개발에 오히려 재설치 비용을 만든다.
- .gitignore에는 비교 worktree 및 새 테스트 캡처에 대한 규칙이 없다. 새로 생성되는 검증 산출물은 전용 ignored 폴더로 모으는 것이 좋다. 이미 추적 중인 캡처는 ignore만 추가해도 Git에서 제거되지 않는다.

## 별도 발견: BGM 배포본 갱신 여부

src/assets/audio/bgm/WebArcBounce.mp3와 WebArcLTR.mp3는 현재 SHA-256이 같은 파일이다. 반면 현재 BGM/의 두 원본은 SHA-256과 크기가 서로 다르며 levels.json의 기록된 원본 해시와도 일치하지 않는다. 나머지 두 원본의 해시 역시 기록과 달라졌다.

기존 LEVELS.md는 당시 두 원본이 같았다고 기록한다. 현재 원본이 바뀐 것으로 보이므로, 배포 음원 정규화 결과와 문서가 갱신되지 않았을 가능성이 있다. 원본을 기준으로 다시 측정·정규화하고 확인할 사안이며, 동일한 배포 MP3 두 개 중 하나를 단순 삭제할 사안이 아니다. Vite는 현재 동일한 배포 파일을 한 자산으로 합치고 있어 배포 용량을 두 배로 낭비하지도 않는다.
